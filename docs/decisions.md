# Журнал технических решений

Формат записи: Problem → Baseline → Experiment → Measurement → Decision → Trade-off.
Инструмент подключается только при появлении конкретной измеримой проблемы.

## Цель и проблема проекта

- **Цель:** независимая проверка готовой кредитной скоринговой модели (качество данных, качество предсказаний, стабильность, надёжность оценок).
- **Проблема:** результатам скоринга нельзя доверять без независимой проверки. Нужна платформа, которая принимает `y_true`, `y_score`, признаки и даты и возвращает структурированный отчёт.
- **Ограничение:** это исследовательский инструмент, а не система одобрения кредитов.

## План (фазы)

1. Data Foundation (A1) - данные, target, утечки, EDA.
2. Baseline Modeling (A2) - Logistic Regression, временное тестирование.
3. Validation Engine (A3) - пакет валидации.
4. Product Interface (A4) - FastAPI + интерфейс.
5. Monitoring (A5).
6. User Validation (A6).

Если фаза не удалась: возвращаемся на шаг назад, фиксируем причину в этом файле и пересоставляем план.

## D-001. Стек для фазы A1

- **Problem:** нужен воспроизводимый pipeline подготовки данных.
- **Baseline:** pandas + Parquet (pyarrow), pytest, PyYAML.
- **Experiment:** пока не требуется - данных нет, объём не измерен.
- **Measurement:** будет выполнено после загрузки реального датасета (память, время чтения).
- **Decision:** DuckDB, Polars, PySpark, MLflow не подключаются. Условие подключения DuckDB: после оптимизации типов и столбцов данные не помещаются в память или SQL-запросы слишком тяжёлые.
- **Trade-off:** при очень большом файле pandas может потребовать чтения по частям.

## D-002. Определение target

- **Problem:** статус `Current` и другие незавершённые статусы не означают «хороший» кредит.
- **Baseline:** итоговый статус кредита (Lending Club не содержит даты дефолта).
- **Decision:** `Fully Paid` = 0; `Charged Off`, `Default` и их варианты "Does not meet the credit policy" = 1; остальные статусы исключаются как незрелые.
- **Trade-off:** это не фиксированный 12-месячный горизонт, а итоговый исход. Из-за этого на поздних периодах выборки есть смещение зрелости: недавние кредиты чаще успевают только до статуса Current и исключаются.

## D-003. Контроль временной утечки

- **Problem:** признаки, появляющиеся после выдачи кредита (платежи, возвраты, последний FICO), раскрывают исход.
- **Decision:** явные списки признаков, доступных на момент выдачи, и признаков утечки. Всё неизвестное требует ручной проверки. Автоматическая проверка только выявляет подозрительные признаки и не подтверждает утечку.

## Измерения фазы A1 (реальный датасет)

- **Источник:** Lending Club, `accepted_2007_to_2018Q4.csv` (2 260 701 строка, 151 столбец, ~1.6 ГБ). Лежит в `data/raw/`, в Git не попадает.
- **Ingestion CSV → Parquet:** 108 с.
- **Память, все 151 столбец:** 17.2 ГБ в pandas. `clean` на полном наборе падает с `MemoryError` (выделение 1.5 ГБ при ~11 ГБ свободных из 15.7 ГБ).
- **Память, 27 столбцов после `prepare`:** 1.04 ГБ (признаки на момент выдачи, числа в float32). Время подготовки 18.6 с, Parquet 36 МБ.
- **Target:** 1 348 099 строк, доля дефолтов 19.98% (269 360). Статусы `Current`, `Late`, `In Grace Period` и пустые исключены.
- **Дефолт по годам выдачи:** 2007 - 26.2%, 2009 - 13.7%, 2013 - 15.6%, 2015 - 20.2%, 2016 - 23.3%, 2017 - 23.1%, 2018 - 15.8%. Падение в 2018 согласуется со смещением зрелости из D-002 (причину отдельно не проверяли).
- **Сильные одномерные связи с target:** `last_fico_range_high` AUC 0.94, `recoveries` 0.84, `total_pymnt` 0.76. Все три в `KNOWN_LEAKAGE`.

## D-004. Память и выбор инструмента

- **Problem:** полный набор (17.2 ГБ в pandas) не помещается в память при очистке.
- **Baseline:** pandas + Parquet, чтение только нужных столбцов (`pyarrow` читает выбранные столбцы без загрузки остальных), оптимизация типов (float32), одна копия при фильтрации в `build_target`.
- **Measurement:** 17.2 ГБ → 1.04 ГБ, 18.6 с на всю подготовку.
- **Decision:** DuckDB не подключается. Условие из D-001 (данные не помещаются после оптимизации типов и столбцов) не выполнено.
- **Trade-off:** при расширении набора признаков (например, добавлении полей кредитного бюро) память вырастет. Тогда замер повторить, а до этого решение не пересматривать.

## D-005. Ограничение проверки утечки по порогу AUC

- **Problem:** `flag_suspicious` с порогом 0.85 пометила только `last_fico_range_high`. `recoveries` (0.844) и `total_pymnt` (0.759) порог не прошли, хотя это утечка по смыслу.
- **Decision:** главным остаётся явный список `KNOWN_LEAKAGE`, составленный по смыслу поля. AUC-проверка служит дополнительным сигналом для незнакомых признаков.
- **Trade-off:** слабая утечка (AUC ниже порога) этим способом не находится. Порог не снижали: это дало бы ложные срабатывания на `int_rate` (0.68).
- **Дополнительно:** `loan_status` оставлен в processed-файле только для аудита target. В обучение он не входит, `split_features` относит его к утечке.

## D-006. Временные границы (фаза A2)

- **Problem:** выбрать train / valid / test по дате выдачи так, чтобы в оценке не было сильного смещения зрелости.
- **Measurement:** доля кредитов в статусе `Current` (исключаются из target): 36 месяцев - 0% для 2014-2015, 26.8% для 2016, 57.4% для 2017. 60 месяцев - 16.3% для 2014, 31.3% для 2015, 42.8% для 2016.
- **Decision:** train до 2013-12-31 (230 706 строк, дефолт 15.65%), valid 2014 (223 103, 18.45%), test 2015 (375 546, 20.19%). Период 2016+ (518 744 строки, 22.42%) помечен `late`: в оценке качества не участвует, нужен для мониторинга (A5).
- **Trade-off:** 2015 год - компромисс. Для 36-месячных кредитов он зрелый, для 60-месячных нет: 31.3% из них исключено как `Current`, значит доля дефолтов в тесте для 60-месячных, вероятно, смещена (направление смещения не проверяли). Более ранний test сделал бы оценку чище, но удалил бы от периода, на котором модель будет применяться.
- **Наблюдение, не объяснено:** доля дефолтов 36-месячных кредитов скачет с 16.1% (2016Q1) до 22.4% (2016Q2). Причину не искали.

## D-007. Baseline: Logistic Regression

- **Baseline:** `LogisticRegression` (lbfgs, без `class_weight`, чтобы вероятности остались пригодными для оценки калибровки). Предобработка внутри `Pipeline`: обрезка выбросов по квантилям 1%/99%, медианная импутация с индикаторами пропусков, стандартизация, one-hot с `min_frequency=100`. Всё оценивается только на train.
- **Выбор C:** expanding-window внутри train (проверка на 2012 и 2013), valid и test не участвуют. Лучший C = 0.01, но разница мала: CV AUC 0.6824 / 0.6811 / 0.6804 для C = 0.01 / 0.1 / 1.0.
- **Итоговая модель:** обучена на train + valid, test использован один раз.
- **Два набора признаков:**
  - `full` - все признаки при выдаче, включая `int_rate`, `grade`, `sub_grade`. Это оценки самого Lending Club, то есть чужая модель.
  - `no_lc_score` - без этих трёх признаков.

| Набор | valid AUC | test AUC | test Gini | test KS | test Brier |
|---|---|---|---|---|---|
| full | 0.7085 | 0.7315 | 0.4630 | 0.3368 | 0.1442 |
| no_lc_score | 0.6990 | 0.7199 | 0.4397 | 0.3183 | 0.1456 |
| тривиальный ориентир (доля дефолтов train) | - | 0.5000 | 0.0 | 0.0 | 0.1632 |

- **Калибровка на test (full):** средняя предсказанная вероятность 0.171 против фактической доли дефолтов 0.202. Верхний дециль: предсказано 0.399, фактически 0.499. Модель систематически занижает риск. Вероятная причина - рост доли дефолтов от периода к периоду (15.65% → 18.45% → 20.19%), то есть сдвиг базовой доли. Гипотеза не проверена: например, не сравнивалась калибровка внутри одного возраста кредитов. Для валидатора это реальный случай плохой калибровки.
- **Наблюдение, не объяснено:** test AUC (0.73) выше valid AUC (0.71) и CV AUC (0.68). Причину не выясняли, поэтому разницу в 0.02 нельзя считать улучшением модели.
- **Выводы по `no_lc_score`:** без оценок Lending Club AUC ниже на 0.012-0.019, то есть большая часть качества не зависит от них.
- **Квартальный AUC на test (full):** 0.7243, 0.7257, 0.7398, 0.7339.

## D-008. Инструменты в фазе A2

- **CatBoost / LightGBM:** не подключены. Критерий из плана (логистическая регрессия даёт неприемлемый результат и бустинг выигрывает на временной валидации) не проверен: порог «неприемлемого» не задан, бустинг не пробовали. Для цели проекта (проверка чужой модели) достаточно baseline.
- **MLflow:** подключён, см. D-009.
- **Optuna:** не нужна. Единственный гиперпараметр C подбирается перебором по сетке из трёх значений.
- **Out-of-time предсказания:** `data/processed/predictions_full.parquet` и `predictions_no_lc_score.parquet` (столбцы `id`, `issue_d`, `split`, `y_true`, `y_score`), 1 117 393 строки, пропусков и повторов `id` нет. Вход для тестов валидатора в A3.

## D-009. MLflow (этап A2.4)

- **Problem:** `run()` перезаписывает один файл `experiments/baseline_metrics.json`. Каждый новый запуск стирает прошлый результат, а версия данных, версия кода и параметры рядом с метриками не сохраняются. В A3 валидатор придётся сравнивать на нескольких наборах предсказаний, в A5 нужны повторные запуски. Без истории сравнить запуски невозможно.
- **Baseline:** JSON-файл с последним результатом. Проблема перезаписи подтверждена по коду, а не измерена отдельно.
- **Decision:** MLflow с локальным хранилищем SQLite (`experiments/mlflow.db`, без сервера). Каждый запуск пишет параметры (границы периодов, лучший C, число признаков, SHA-256 файла данных, коммит git), метрики по valid/test/late и JSON как артефакт. Слой отделён (`src/models/tracking.py`), флаг `--no-track` отключает запись.
- **Проверка:** установка не сломала numpy 2.4.4, pandas 2.3.0, scikit-learn 1.8.0. Все 28 тестов проходят, четыре из них новые. Один из тестов подтверждает, что второй запуск не затирает первый.
- **Trade-off:** зависимость тяжёлая (mlflow 3.17.2 тянет flask, docker, databricks-sdk и другие пакеты), поэтому в `pyproject.toml` она необязательная (`tracking`). SQLite подходит для одного пользователя. Для нескольких понадобится отдельный сервер (PostgreSQL в плане).
- **Ограничение:** до первого коммита git поле `git.commit` равно `no-commit`, поэтому код запуска пока не привязан к версии. Прежде чем опираться на историю запусков, нужно сделать коммит.
- **Инцидент:** первый запуск записался в MLflow, хотя команда вернула код 1. Вероятная причина: PowerShell считает вывод в stderr ошибкой (текст ошибки я не смотрел). Запуск повторил, дубликат `baseline-lr-v1` удалил через `mlflow.delete_run`. Удаление мягкое: строка в БД остаётся с пометкой deleted.

## D-010. Пакет валидации (фаза A3): архитектура и собственные метрики

- **Problem:** нужен пакет, который проверяет чужую модель по `y_true`, `y_score` и необязательным признакам, датам, группам и референсным данным, не доверяя метрикам самой модели.
- **Decision:**
  - структура из плана: `src/validation/{data_quality, informativeness, performance, calibration, stability, reliability, diagnostics, explainability, reporting}`;
  - четыре точки входа: `validate_dataset`, `assess_informativeness`, `evaluate_predictions`, `run_full_validation`, модули работают независимо;
  - собственные реализации на numpy: ROC-AUC (через ранги с усреднением при совпадениях), Gini, KS, PR-AUC, Brier, Log Loss, Precision/Recall/F1/Balanced Accuracy, ECE, кривая калибровки, PSI, IV/WoE, VIF, стратифицированный и групповой bootstrap;
  - scikit-learn используется только для Mutual Information (оценка по k соседям) и в тестах как эталон.
- **Ключевое правило:** если метрика не определена (один класс, мало наблюдений, нулевой знаменатель), результат имеет `status="not_computable"` и `value=None`, а не число. Это проверено тестами для AUC, Gini, KS, PR-AUC, Precision, PSI, IV, Mutual Information, bootstrap.
- **Формат результата:** каждая проверка возвращает `MetricResult` (значение, объяснение, интерпретация, ограничения, детали). Отчёт `ValidationReport` сохраняется в HTML (основной, графики встроены), PDF (reportlab, нужен шрифт Arial или DejaVu с кириллицей, иначе ошибка, а не нечитаемый PDF) и JSON.
- **Проверка корректности:** метрики сверены с scikit-learn с точностью до 1e-12 на данных с совпадающими значениями скора, плюс ручные расчёты (AUC на 4 точках, Brier, ECE, PSI, IV). При сверке найдены и исправлены два расхождения: `log_loss` клипует скор машинным эпсилон (как scikit-learn 1.8), а не 1e-15, граница корзины калибровки попадает в нижнюю корзину.
- **Тесты:** 10 сценариев плана (`tests/test_validation_scenarios.py`), сверка с эталоном, точки входа, отчёты. Всего в проекте 81+ тест.
- **Trade-off и ограничения:**
  - пороги интерпретации (AUC, PSI 0.1/0.25, IV 0.02/0.1/0.3/0.5, ECE 0.05, VIF 10 и др.) - общепринятые рабочие ориентиры, а не строгие стандарты. В тексте каждого результата это указано;
  - стратифицированный bootstrap предполагает независимость наблюдений, групповой требует ≥ 10 групп;
  - SHAP без доступа к модели не считается: в отчёте стоит `not_computable` с объяснением. SHAP с моделью реализован, но на реальной модели не проверялся;
  - Plotly и Evidently не подключены: HTML-отчёт использует matplotlib. Условие подключения Plotly - нужна интерактивность (A4, Streamlit);
  - сравнение с baseline-моделью на данных пользователя из плана A3 (п. 3.3) не реализовано.

## D-011. Производительность bootstrap

- **Measurement:** на тестовой выборке 2015 года (375 546 строк) один bootstrap ROC-AUC при 20 повторах - 1.3 с, то есть 500 повторов по пяти метрикам по отдельности заняли бы минуты. Метрики сами по себе быстрые (AUC 0.04 с).
- **Decision:** все метрики считаются на общих bootstrap-выборках одним проходом, Gini получается как 2·AUC−1. По умолчанию 500 повторов при ≤ 50 000 строк, иначе 200. Итог: полный отчёт по 375 546 строкам за 26 с вместо 104 с.
- **Trade-off:** при 200 повторах границы интервала менее гладкие. Это указано в ограничениях результата. Параметр `n_boot` можно задать явно.

## Наблюдения фазы A3 на реальных данных

- **Тест 2015 (baseline Logistic Regression, 375 546 кредитов):** AUC 0.7315, 95% интервал [0.7299, 0.7337] (стратифицированный bootstrap). Интервал узкий из-за размера выборки, но он учитывает только случайность выборки, а не смену периода: AUC на valid 2014 был 0.7085, то есть разница между периодами (0.023) на порядок больше ширины интервала.
- **Калибровка:** валидатор помечает занижение риска (средний прогноз 0.171, факт 0.202). Этот результат совпал с ручной проверкой из D-007.
- **Проверка информативности на 300 000 строк (признаки включают заведомо запрещённые):** `last_fico_range_high` (AUC 0.94), `recoveries` (IV 9.1), `total_pymnt` (IV 0.95) попали в IV ≥ 0.5, а `recoveries` и `total_pymnt` не прошли порог AUC 0.85 (см. D-005): IV поймал то, что пропустил одномерный AUC. Это подтверждает, что одной проверки недостаточно.
- **Нестабильность IV по годам:** валидатор пометил `int_rate`, `fico_range_low`, `dti`. Причина не выяснена: это может быть реальный дрейф или незрелость target в поздних годах (D-006).
- **Не сделано:** проверка валидатора на данных чужой модели (это фаза A6) и сравнение с Evidently.
